# Учебная практика ПМ.07 Вариант 07 Салон красоты

Проект содержит воспроизводимые материалы по администрированию PostgreSQL 16: разграничение прав, резервные копии custom с gzip, восстановление в отдельные базы, журналирование и запуск cron. Название репозитория `practica_07_flower_shop` сохранено владельцем; текущая предметная область — **Салон красоты**.

Материалы опубликованы в ветке [codex/pm07-v07](https://github.com/Slug-Blue/practica_07_flower_shop/tree/codex/pm07-v07). Персональная отчетная документация передана отдельно в комплекте для сдачи.

## Фактический стенд и результаты

Опыты выполнены 17.11.2026 на Ubuntu 22.04.5 LTS в отдельном контейнере Docker Desktop 29.2.1. PostgreSQL и клиентские утилиты — 16.16. Пользователь ОС — `student`, часовой пояс — `Europe/Moscow`. Контейнер заменяет учебную Linux-машину для опытов, но не является отдельной VM или постоянно работающим сервером.

Исходная база — `pm07_v07`, ручное восстановление — `pm07_v07_restore`, проверка точного автоматического архива — `pm07_v07_restore2`. В каждой из таблиц `clients`, `masters`, `appointments` подтверждены 4 строки, сумма id 10 и сумма amount 100.00. Все семь полей строки id=1 и `access_probe(1,10)` совпали в трёх базах. Файлы `out/*.compare.txt` и `evidence/comparison.txt` подтверждают сравнение.

Для ролей проверены разрешённые действия admin и app_user, SELECT readonly и четыре запрета по правам. Ручной архив `backups/manual.dump` имеет SHA-256 `e0f346d0996ddeef4df6271ba7f9124486f3bcf58d566df8535f7197acb20e79`. Его размер — 6860 байт. Формат и сжатие проверены оглавлением, пригодность — восстановлением.

Cron действительно запустил задание от student 17.11.2026 в 19:48:01 MSK. Обёртка записала `run_exit=0` в 19:48:02, скрипт создал новый архив и `END result=OK`. Источник системного CMD — `/var/log/syslog`, прочитанный администратором. Кнопка ручного запуска не использовалась для этого подтверждения.

Контролируемый отказ проверен в отдельной копии с `DB=pm07_v07_missing` и действующим профилем: ошибка отсутствующей базы, код 1 и `ERROR`. Повреждённая копия не является резервной копией для восстановления и в каталог backups не включена.

## Состав

- `input.sql` — выданные исходные данные варианта 07 без изменения схемы.
- `grants.sql` — разрешения, выполняется владельцем admin после импорта.
- `verify.sql` — агрегаты, строки id=1, access_probe и параметры соединения.
- `run.sh` — операция варианта, явные `-Fc -Z 6`, журнал START/END/ERROR, дополнение SHA-256.
- `cron-entry.sh` — запись фактического кода завершения планового запуска.
- `config.env.example` — открытый пример конфигурации.
- `setup_lab.sh` — первоначальное создание учебных ролей с автоматически сгенерированными паролями и пустых баз; запускается root только на новом учебном стенде.
- `backups`, `logs`, `out`, `evidence` — реальные результаты опытов. Рисунок 2 — снимок pgAdmin 4 v9.14. Другие figure PNG — читаемые фрагменты сохранённых протоколов, а не снимки терминала. Полные TXT сохранены рядом.

Паролей, действующего `auth/pgpass`, персональных документов и подписей в репозитории нет. `.gitignore` исключает закрытые профили. В архиве резервной копии базы отсутствуют серверные роли: `pg_dump` копирует одну базу, роли создаются отдельно.

## Повторение на подготовленной Ubuntu 22.04 с PostgreSQL 16

Используйте отдельный учебный кластер. Первоначальный администратор должен создать `admin`, `app_user`, `readonly` с LOGIN и без SUPERUSER, CREATEDB, CREATEROLE, а также пустые базы с владельцем admin. Для этого можно использовать `setup_lab.sh`, предварительно скопировав `input.sql` в `/tmp/input.sql`. Скрипт не удаляет и не пересоздаёт уже существующие базы и роли: при совпадении имени он завершится ошибкой. Имена в приведённых командах рассчитаны на пустой стенд.

Скопируйте рабочие файлы в `/home/student/pm07` и передайте их пользователю student. При самостоятельном создании профиля сохраните `auth/pgpass` в формате `host:port:database:user:password`; права — 600, владелец — пользователь запуска. Пароли выбираются локально. Двоеточие и обратный слеш внутри полей экранируются обратным слешем.

```bash
cd /home/student/pm07
cp config.env.example config.env
chmod 600 auth/pgpass
export PGPASSFILE="$PWD/auth/pgpass"
psql -X -w -h 127.0.0.1 -U admin -d pm07_v07 -v ON_ERROR_STOP=1 -f grants.sql
psql -X -w -h 127.0.0.1 -U admin -d pm07_v07 -v ON_ERROR_STOP=1 -f verify.sql
bash ./run.sh
printf 'exit=%s\n' "$?"
tail -n 8 logs/run.log
```

`setup_lab.sh` уже импортирует input.sql. Если базы подготовлены вручную, импортируйте input.sql под admin ровно один раз, перед grants.sql. По умолчанию профиль из setup разрешает admin обращаться к трём учебным базам; фактический пароль не публикуется.

Для ручной копии:

```bash
pg_dump -w -h 127.0.0.1 -U admin -d pm07_v07 -Fc -Z 6 -f backups/manual_new.dump
sha256sum backups/manual_new.dump
pg_restore --list backups/manual_new.dump
pg_restore -w -h 127.0.0.1 -U admin -d pm07_v07_restore \
  --no-owner --no-privileges --exit-on-error backups/manual_new.dump
psql -X -w -h 127.0.0.1 -U admin -d pm07_v07_restore -f verify.sql
```

База назначения должна быть пустой. Для каждого следующего архива создайте администратором ещё одну базу с уникальным именем, например `pm07_v07_restore3`; исходную базу и предыдущие копии не очищайте. Сопоставьте агрегаты и строку id=1 для всех трёх таблиц.

## Проверка ролей

Создавайте отдельное подключение для каждой роли и сначала выполняйте `SELECT current_user;`. Под admin создайте и удалите `check_admin(id int)`. Под app_user выполните INSERT access_probe(9001,20), UPDATE value=30, SELECT и DELETE временной строки. Затем проверьте, что осталась только (1,10). Под readonly отдельно выполните INSERT access_probe(2,20) и DELETE id=1; ожидаются отказы для таблицы. Под app_user отдельно выполните `CREATE TABLE forbidden_app(id int)` и `CREATE ROLE forbidden_probe LOGIN`; ожидаются отказы для схемы и полномочий создания роли. Полные SQL и выводы приведены в `evidence/03-allowed.txt`, `04-readonly-denied.txt`, `05-app-denied.txt`.

## Контролируемый отказ

Сделайте отдельную копию run.sh и config.env. В копии задайте `DB="pm07_v07_missing"`, а AUTH направьте на действующий закрытый профиль. Выполните копию, сохраните код и её `logs/run.log`. Ожидается именно сообщение об отсутствующей базе, а не ошибка пароля. Рабочие файлы не изменяются.

## Планирование

Тестовое расписание устанавливается в crontab пользователя student:

```cron
SHELL=/bin/bash
*/2 * * * * /bin/bash "$HOME/pm07/cron-entry.sh" >> "$HOME/pm07/logs/cron.log" 2>&1
```

Дождитесь чётной минуты. Сверьте системный CMD, `scheduler.log`, новую пару START/END и новый архив. Затем замените тестовую строку одной постоянной:

```cron
SHELL=/bin/bash
0 3 * * * /bin/bash "$HOME/pm07/cron-entry.sh" >> "$HOME/pm07/logs/cron.log" 2>&1
```

Ежедневное время 03:00 MSK выбрано для небольшой учебной базы. Docker Desktop и контейнер должны работать в момент запуска. После завершения учебной проверки контейнер может быть остановлен; тогда расписание не выполняется до его запуска. Журнал cron.log может быть пустым при успешном опыте, поскольку сообщения пишутся в run.log и scheduler.log.

## Дополнение SHA-256

При `CHECKSUM="0"` создаётся обязательный архив и оглавление без sidecar. При `CHECKSUM="1"` скрипт создаёт `.sha256` и выполняет `sha256sum --check`. Для отрицательной проверки копируйте архив и sidecar в отдельный тестовый каталог, меняйте только копию и проверяйте её. SHA-256 не заменяет проверку восстановления.
